# Linux 根分区磁盘满了怎么办？一次完整的排障实录

> **适用场景**：Ubuntu/Debian 系 Linux 服务器根分区（/）使用率达到 100%，需要定位并释放空间。
> **难度等级**：小白友好 | **风险提示**：删除文件前请确认内容，操作前建议备份

---

## 一、问题发现：根分区爆了

某天登录服务器执行 `df -h`，发现根分区 `/` 使用率已经到了 **100%**：

![df -h 初始状态](img.wanzf.com/i/260527203429.png)

```
文件系统      Size  Used Avail Use% Mounted on
/dev/nvme0n1p2  938G  888G  2.1G  100%   /
```

938G 的分区用了 888G，只剩 **2.1G** 可用空间。系统虽然还没完全卡死，但随时可能出问题——日志写不进去、临时文件创建失败、甚至服务异常退出。

**第一反应**：谁把磁盘吃光了？

---

## 二、第一步：用 du 找大户

最直觉的做法是用 `du` 命令从根目录开始逐层扫描，看看哪些目录占用了最多空间：

```bash
du -h --max-depth=1 --one-file-system / 2>/dev/null | sort -hr | head -20
```

参数说明：
- `-h`：人类可读格式（显示 G/M/K）
- `--max-depth=1`：只看一级子目录，不递归深入
- `--one-file-system`：不跨分区扫描（避免扫到挂载的其他磁盘）
- `sort -hr`：按大小倒序排列

### ⚠️ 第一个坑：忘记加 sudo

第一次执行时没加 `sudo`，结果出来了：

![du 无 sudo 结果](img.wanzf.com/i/260527203405.png)

```
167G    /home
86G     /home/huajie
3.9G    /home/yesheng
...
```

**等等，这不对！** `df` 显示用了 888G，但 `du` 只算出来 167G？差了 **700 多 G**！

原因很简单——**没有 sudo 权限，`du` 跳过了所有无权访问的目录**（其他用户的 home 目录、`/var/lib/docker`、`/var/lib/containerd` 等）。这些目录被静默跳过了，但它们的空间仍然真实占用着磁盘。

**教训：排查系统级问题时，一定要加 sudo！**

加上 sudo 后重新执行：

```bash
sudo du -h --max-depth=1 --one-file-system / 2>/dev/null | sort -hr | head -20
```

这次数字对上了——**731G 在 `/home` 目录下**，是绝对的大户。

## 三、第二步：深挖 /home，继续钻取

锁定 `/home` 后，继续向下钻取，看各用户占了多少：

```bash
sudo du -h --max-depth=1 /home | sort -hr
```

| 用户 | 占用 |
|------|------|
| max | 317G |
| ps | 248G |
| huajie | 93G |
| tangy | 57G |
| 其他用户 | ~16G |

重点看最大的两个用户 `max` 和 `ps`，分别继续深挖：

```bash
sudo du -h --max-depth=1 /home/max | sort -hr | head -20
sudo du -h --max-depth=1 /home/ps | sort -hr | head -20
```

## 四、第三步：检查已删除但仍被占用的文件（重要！）

Linux 中有一种特殊情况：**文件已经被 `rm` 删除了，但如果还有进程持有该文件的句柄，磁盘空间不会释放。**

检查方法：

```bash
sudo lsof +L1 2>/dev/null | awk 'NR==1 || $7 > 0' | sort -k7 -rn | head -30
```

- `+L1`：只显示已删除（链接数为 0）的文件
- `$7 > 0`：过滤掉大小为 0 的条目
- `sort -k7 -rn`：按文件大小倒序排列

在本案例中，lsof 只找到少量 KB 级的小文件（pipewire 音频缓存），**排除此可能性**。但这个步骤不能跳过，因为它是导致"删了文件空间不释放"的头号原因之一。

---

## 五、第四步：逐一确认并清理

经过层层钻取，最终确认了以下可清理的项目：

### 🗑️ 清理项一：VMware 拖拽缓存（109G）

位置：`/home/ps/.cache/vmware/drag_and_drop/`

这是 VMware 虚拟机的拖拽传输缓存——每次从主机往虚拟机拖拽文件时，VMware 会先在宿主机上生成一份临时副本。时间久了这些副本堆积如山。

**清理命令：**
```bash
rm -rf ~/.cache/vmware
```

纯垃圾文件，删除后 VMware 需要时会自动重建，不影响任何正在运行的虚拟机。

### 🗑️ 清理项二：回收站未清空（60G）

位置：`/home/ps/.local/share/Trash/`

没错，**60GB 的文件躺在回收站里**。Linux 的每个用户都有自己的回收站（`~/.local/share/Trash`），文件"删除"后只是移到这里，并没有真正释放空间。

**清理命令：**
```bash
# 方法一：find 方式（推荐，文件多时更可靠）
sudo find /home/ps/.local/share/Trash -mindepth 1 -delete

# 方法二：直接删掉整个目录再重建
sudo rm -rf /home/ps/.local/share/Trash
sudo mkdir -p /home/ps/.local/share/Trash/files /home/ps/.local/share/Trash/info
sudo chown -R ps:ps /home/ps/.local/share/Trash
```

> 💡 **小贴士**：如果用 `rm -rf .../*` 通配符清理时发现文件还在，是因为 shell 展开通配符有上限。改用 `find ... -delete` 或直接 `rm -rf 整个目录` 更可靠。

### 🗑️ 清理项三：pip 缓存（20G）

位置：`/home/max/.cache/pip/`

Python 的 pip 包管理器会把下载过的安装包缓存在本地，方便下次安装时复用。但这些缓存会不断膨胀。

**清理命令：**
```bash
pip cache purge          # 清理当前用户 pip 缓存
sudo rm -rf /path/to/user/.cache/pip  # 直接删除指定用户的缓存
```

这只是下载缓存，**不会影响已安装的任何包**，放心清。

三项清理完成后，执行 `df -h` 验证：


| 指标 | 清理前 | 清理后 | 变化 |
|------|--------|--------|------|
| 已用空间 | 888G | 700G | ⬇️ **188G** |
| 可用空间 | 2.1G | 190G | ⬆️ **+188G** |
| 使用率 | 100% 🔴 | 79% 🟢 | ✅ 正常 |

根分区从满载状态恢复到健康水平。

## 七、完整排查流程图

```
df -h 发现根分区 100%
        │
        ▼
  sudo du 定位大目录（⚠️ 必须加 sudo！）
        │
        ├── /home 是大户 → 继续深挖各用户
        │       │
        │       ├── ps 用户 → .cache/vmware (109G) + .local/share/Trash (60G)
        │       └── max 用户 → .cache/pip (20G) + database/miniconda3 等
        │
        ├── sudo lsof +L1 检查僵尸文件句柄
        │
        └── sudo docker system df（如有 Docker）
                │
                ▼
        分类处理：
        ├─ 安全清理（缓存/回收站）→ 直接删
        ├─ 迁移（大数据目录）→ mv + ln -s 到空闲分区
        └─ 重启进程（僵尸句柄）→ kill/restart 对应服务
```

## 八、常见"吃磁盘"的元凶速查表

| 类型 | 典型路径 | 危险程度 | 处理方式 |
|------|---------|---------|---------|
| 日志文件 | `/var/log/*` | 低 | `logrotate` 或手动清 |
| systemd 日志 | journalctl 管理 | 低 | `journalctl --vacuum-size=500M` |
| Docker 数据 | `/var/lib/docker` | 中 | `docker system prune -a` |
| 回收站 | `~/.local/share/Trash` | 极低 | 直接清空 |
| pip 缓存 | `~/.cache/pip` | 极低 | `pip cache purge` |
| npm 缓存 | `~/.cache/npm` | 极低 | `npm cache clean --force` |
| conda 环境 | `~/miniconda3` | 中 | 迁移或删除不用环境 |
| HuggingFace 缓存 | `~/.cache/huggingface` | 低-中 | 确认模型不再需后删除 |
| VMware 缓存 | `~/.cache/vmware` | 极低 | 直接删 |
| 浏览器缓存 | `~/.cache/mozilla` | 极低 | 自动清理即可 |
| 已删除但被占用 | lsof +L1 查看 | 视情况 | 重启对应进程 |

## 九、如果文件都不能删，怎么扩容根分区？

清理缓存和迁移目录虽然能解燃眉之急，但根分区本身的容量并没有变。如果所有文件都"很重要"不能删，就需要考虑**真正意义上的扩容**。以下从简单到复杂列出五种方案：

### 方案一：软链接 / Bind Mount 迁移目录（推荐，最安全）

**核心思路**：把根分区上的大目录搬到其他空闲磁盘，再用软链接或 bind mount 映射回来，对应用完全透明。

```bash
# 软链接方式（简单直接）
sudo mv /home/max/database /mnt/sda/max_database
sudo ln -s /mnt/sda/max_database /home/max/database

# Bind mount 方式（更底层，连应用都感知不到变化）
# 适合迁移 /var/lib/docker、/var/lib/containerd 等系统目录
sudo mv /var/lib/docker /mnt/sda/docker
sudo mkdir /var/lib/docker
# 写入 /etc/fstab 实现开机自动挂载
echo '/mnt/sda/docker  /var/lib/docker  none  bind  0  0' | sudo tee -a /etc/fstab
sudo mount /var/lib/docker
```

**优点**：零风险，不碰分区表，随时可回退
**缺点**：治标不治本，根分区的实际容量没变
**本例适用性**：✅ `/mnt/sda` 有 1.1T 空闲，完全够用

### 方案二：缩小相邻分区，扩展根分区

**核心思路**：把根分区旁边的分区缩小，腾出的空间分配给根分区。

```
扩容前：
| p1(efi) | p2(root 938G) |  磁盘尾部未分配空间  |

扩容后：
| p1(efi) | p2(root 更大)  |
```

前提条件：**根分区右侧必须有未分配空间**。如果紧挨着其他分区，就需要先缩小邻居，操作链变长。

操作步骤（需要 Live USB 启动）：
```bash
# 1. 用 Ubuntu Live USB 引导启动
# 2. 打开 GParted 图形工具
# 3. 缩小相邻分区 → 将释放的空间分配给根分区 → 应用
```

**优点**：根分区真正变大
**缺点**：需要停机，有一定数据风险，需要 Live USB
**本例适用性**：❌ 根分区已占满整块 NVMe，右侧没有未分配空间

### 方案三：LVM 逻辑卷扩容

如果你的系统安装时选择了 LVM（逻辑卷管理），扩容会非常灵活：

```bash
# 检查是否使用了 LVM（如果分区名是 /dev/mapper/... 说明用了 LVM）
sudo lvs

# 如果是 LVM，操作如下：
# 1. 把新磁盘加入卷组
sudo pvcreate /dev/sdb                          # 将新磁盘初始化为物理卷
sudo vgextend ubuntu-vg /dev/sdb                 # 加入卷组

# 2. 扩展逻辑卷，用尽所有可用空间
sudo lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv

# 3. 在线扩展文件系统（ext4 支持在线扩容，不用卸载！）
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv
```

**优点**：不停机，不丢数据，在线扩容，LVM 的杀手级功能
**缺点**：安装时必须选择 LVM，普通分区无法事后转换
**本例适用性**：❌ 分区名为 `/dev/nvme0n1p2`（直接分区），未使用 LVM

### 方案四：换一块更大的磁盘（最彻底）

买一块更大的磁盘（比如从 1T 升到 2T），整盘克隆过去，然后扩展分区：

```bash
# 1. 克隆整块盘（用 Clonezilla 更安全，或 dd 直拷）
sudo dd if=/dev/nvme0n1 of=/dev/nvme0n1 bs=4M status=progress

# 2. 克隆完成后，扩展分区和文件系统
sudo growpart /dev/nvme0n1 2      # 扩展第 2 个分区到磁盘末尾
sudo resize2fs /dev/nvme0n1p2     # 在线扩展 ext4 文件系统
```

**优点**：根治问题，获得完整的新容量
**缺点**：需要停机，需要硬件投入，克隆时间长

### 方案五：云服务器在线扩容（最省心）

如果你的服务器在阿里云、腾讯云、AWS 等云平台上，这是最简单的方案：

```
控制台操作：云盘 → 扩容（比如 938G → 2T）→ 确认
```

然后在服务器内执行两行命令：

```bash
sudo growpart /dev/nvme0n1 2       # 让分区识别新的磁盘大小
sudo resize2fs /dev/nvme0n1p2      # 让文件系统使用新空间
```

**不停机、不丢数据、不换硬件**，这是云服务器的一大优势。

### 五种方案对比总结

| 方案 | 难度 | 是否停机 | 是否丢数据 | 适用场景 |
|------|------|---------|-----------|---------|
| 软链接迁移 | ⭐ | 不停机 | 不丢 | 临时/长期都适用 |
| Bind mount | ⭐⭐ | 不停机 | 不丢 | 迁移系统目录 |
| 缩邻扩根 | ⭐⭐⭐ | 需停机 | 有风险 | 有空闲空间 |
| LVM 扩容 | ⭐⭐ | 不停机 | 不丢 | 已使用 LVM |
| 换大盘 | ⭐⭐⭐⭐ | 需停机 | 克隆可保障 | 彻底解决 |
| 云盘扩容 | ⭐ | 不停机 | 不丢 | 云服务器 |

> 💡 **建议**：对于物理服务器，优先选**方案一（软链接迁移）**——零风险、不停机、效果立竿见影。只有当所有文件都不能迁移，且确实需要更大根分区时，再考虑方案二到四。如果是云服务器，方案五是首选。

## 十、长期预防建议（附加题）

### 1. 设置自动清理 cron 任务

```bash
# 编辑 crontab
sudo crontab -e

# 每周日凌晨 3 点自动清理缓存和回收站
0 3 * * 0 find /home/*/.local/share/Trash -mindepth 1 -delete 2>/dev/null
0 3 * * 0 find /home/*/.cache/vmware -type d -exec rm -rf {} + 2>/dev/null
```

### 2. 大数据目录迁移到空闲分区

如果有其他磁盘有空闲空间（本例中 `/mnt/sda` 有 1.1T），可以把大目录迁移过去：

```bash
# 示例：迁移 database 目录（108G）
sudo mv /home/max/database /mnt/sda/max_database
sudo ln -s /mnt/sda/max_database /home/max/database
```

软链接对应用完全透明，不需要修改任何配置。

### 3. 配置日志轮转

编辑 `/etc/logrotate.conf` 或在 `/etc/logrotate.d/` 下添加配置，确保日志文件不会无限增长：

```bash
/var/log/myapp/*.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
}
```

### 4. 监控告警

设置磁盘使用率监控告警（比如超过 85% 就发通知），避免下次又突然爆满：

```bash
# 简单脚本示例：写入 crontab 每小时检查
* * * * * df / | awk 'NR==2 && int($5) > 90 {print "警告: 根分区使用率 "$5}'
```

## 十一、总结

本次排障的核心经验有三点：

1. **`du` 必须加 sudo** — 无 sudo 时大量目录被静默跳过，数字严重失真，这是最容易踩的坑
2. **不要忽略回收站** — 60G 文件静静躺在回收站里，很多人以为删了就没了
3. **VMware 拖拽缓存是个隐形杀手** — 109G 的临时文件堆积，很多人根本不知道它的存在

排查磁盘问题的核心思路就是**逐层钻取**：先 `df` 看"哪里满了"，再用 `du` 找"谁吃的"，最后针对性处理。如果清理不了，还有软链接迁移、LVM 扩容、云盘扩容等多种后路。掌握了这个流程，90% 的磁盘满问题都能解决。
